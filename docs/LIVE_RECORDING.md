# Bounded live recording (Mode 01 software path)

The Scan screen offers codes-only, one-pass sensor snapshot, and Live recording. Recording borrows the home screen's shared connection to the saved scanner ([vehicle startup](VEHICLE_STARTUP.md)); it opens no connection of its own. Preparation reads the support map and stored/pending generic emissions codes once. Only positively advertised readings in the implemented scalar catalog can be selected, from one to four distinct PIDs. One PID can yield separate ECU responder rows. ECU IDs such as `7E9` identify a response source; the app does not assign a vehicle module name.

Start polls sequentially under the core's shared write gate. Pause finishes an in-flight reply but admits no later write until Resume; Stop publishes a final or partial record. Preparation, pauses and polling share a ten-minute monotonic limit, a 500 ms minimum spacing between completed writes, and caps of 1,200 completed writes, three retries total and 10,000 sample rows. Backgrounding or losing the connection stops the session and keeps the partial result for Save or Discard. Every recording finish closes the vehicle connection, including a user Stop, failure or limit: even a completed record can have interrupted an in-flight reply. A new session requires explicit reconnection and fresh preparation. The screen never reconnects or resumes automatically.

Trends group by PID, responder and recorded unit. The default 60-second view and All recorded option use elapsed observation times. Missing and failed reads, pauses, unit changes and gaps over five seconds break lines; single observations are points. Previous and Next sample controls give each actual observation's time, ECU, unit and status. Five seconds is a provisional display stale threshold, not a vehicle fault threshold. Values after a failed or missing read remain labeled as last observed.

This is a generic emissions read-only software implementation. The synthetic tests and hosted Android build do not establish behavior on any vehicle or adapter. Hardware use follows the separate owner-operated gate in [LIVE_TEST_GATE.md](LIVE_TEST_GATE.md).

## Competing hypotheses and falsification

These hypotheses concern the meaning of a particular future field. Several representations could coexist in one module. Failing to locate a field does not falsify its existence.

| Hypothesis | Evidence for; evidence against or missing | Falsification using lawful existing evidence |
| --- | --- | --- |
| H1: a field directly encodes remaining distance/time | The desired display and public schema support this representation; no Cayenne field has been identified. | With fixed conditions and a documented unit/scale, a candidate increasing by the known elapsed amount contradicts a simple countdown. An applicable field definition can settle it directly. |
| H2: a field encodes elapsed distance/time; remaining is derived from a separate interval | The Touareg documentation makes this a concrete related-platform alternative. No Porsche transfer is established. | A candidate that decreases rather than increases with elapsed distance/time contradicts this simple model. The applicable interval must also be sourced; a nominal service schedule is not enough. |
| H3: a field is an absolute due-at odometer/time value | Constant anchors can produce changing countdowns. This is an analytical alternative, without direct target-field evidence. | A raw value changing with every unit of driving contradicts a constant anchor over that window. Date epoch, calendar conventions and rounding must be documented before applying the time case. |
| H4: a field is last-service mileage/date, combined with a configured interval | The Abrites distinction makes this a useful target-specific vendor-supported possibility. Its wire realization remains unknown. | Existing labelled prior-service data or an exact definition can distinguish this from H3. Constant bytes alone cannot: both hypotheses predict a stationary anchor. |
| H5: oil countdowns are adjusted dynamically while inspection uses fixed counters | Regional VW/Audi strategies show why fixed subtraction is not universal. No dynamic algorithm is established for this Cayenne. | An exact fixed-field definition can reject this hypothesis for that field. Short observations matching a straight line cannot prove fixed behavior or disprove dynamic behavior. |
| H6: the cluster is accessible through a read service supported by the owned adapter | Vendor cluster coverage and the desktop transmission fixture make further documentary research reasonable. Different modules/protocols, prerequisites and adapter features remain competing explanations. | An applicable route requiring unavailable adapter behavior or state-changing prerequisites defeats this route within current scope. A transmission fixture or another adapter's success cannot resolve it. |

Confidence in H1 through H5 as possible interpretations is distinct from confidence in target applicability: target applicability is unknown for all of them. H4 now has stronger vendor-level support than an entirely invented counter model. H6 remains conditional.

## Selected offline experiment and alternatives

The recommended deliverable is a small Kotlin/JUnit counter-hypothesis experiment confined to test sources. It evaluates a finite declared list of candidate interpretations against newly constructed observations. It returns every mathematical fit and explicit rejection reasons. It never ranks a plausible-looking fit, identifies an ECU, or emits a supported vehicle definition.

This choice follows the desktop proposal and uses existing dependencies. A prose-only ledger is cheaper but cannot execute the ambiguity examples. A new generic transport/identifier matcher would add scope while repeating framing work already delivered in #61. Importing a public schema or adding an ODX parser adds dependencies/data concerns without providing the missing field.

The experiment must demonstrate:

- A single observation cannot choose byte order, sign, scale or semantics merely because one number looks reasonable.
- A second observation can reject some hypotheses using declared changes in distance/time; constant anchors still leave due-at versus last-service ambiguous.
- Missing units, field width/category, inconsistent field identity, incorrect payload length or invalid byte values produce no interval result.
- All-ones bytes remain unresolved unless the synthetic candidate explicitly declares numeric versus unavailable meaning. Negative values are not automatically evidence of an overdue counter.
- Distance and time, and oil/intermediate/main categories, cannot be silently mixed. Unknown or related-platform-only applicability is preserved even when only one mathematical fit remains.

Example, entirely synthetic: at odometers 48,300 then 48,350, a prior-service anchor of 41,500 and configured distance of 15,000 yield 8,200 then 8,150 remaining. An absolute due anchor of 56,500 yields the same outputs. Matching these displayed numbers cannot distinguish the raw fields. These values are not a Porsche schedule. Time examples use an abstract day coordinate, never an inferred epoch or the host clock.

This difference is in those implementations, not proof that UDS permits mismatches or that the entire library lacks another check. Thus a recognized service and identifier prefix still do not define the remaining payload. This supplies no Cayenne codec or route. |

Confidence is high in these inspected source-code distinctions and remains unknown for the target protocol. Scapy's files carry GPL-2.0-only notices; `ecu_diagnostics`' [manifest](https://raw.githubusercontent.com/rnd-ash/ecu_diagnostics/main/Cargo.toml) declares GPL-3.0-only and version 0.107.5. No reuse or new dependency is proposed. Public snippets involving other modules, unspecific programming coverage or different generations were not used to identify the cluster.

The parser comparison supports this inference: a positive envelope compatible with both families cannot select one, even if its framing and identifier echo are correct. A decoder library's chosen class can supply a name that the bytes alone do not establish. An error label can likewise depend on the assumed family; retain the raw code and family uncertainty. Neither fact warrants a live protocol-discovery request.

No additional implementation is recommended during the current counter experiment. The repository already tests generic service/PID echo matching, incorrect lengths and malformed negative replies in `MalformedAndStatusTest`; the new experiment addresses counter semantics. A standalone protocol classifier without target evidence would add no vehicle knowledge. If a future bounded parser experiment is useful, its distinct assertions should be exact matching of both identifier bytes, definition-dependent payload length, and retention of both compatible protocol interpretations. It should use constructed payloads with symbolic field identities, without a vehicle address list, request generator or automatic protocol selection. That is a possible independent research experiment, not an extension silently added to the current plan.

The cluster route/read-service question remains open. Public documentary research can continue independently, especially where an exact module/software description or original sanitized record can distinguish tool configuration from observed protocol. This result introduces no new source-search stop condition.
